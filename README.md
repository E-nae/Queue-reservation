# 대기열 예매 시스템 (Virtual Waiting Room)

> 티켓 예매처럼 짧은 시간에 요청이 몰리는 상황을 가정하고 만든 가상 대기열 시스템입니다.
> Redis 자료구조로 선착순 순서를 보장하고, 결제 시점의 재고 차감을 Lua Script로 원자적으로 처리해 초과 판매를 막는 것이 목표였습니다.

**Live Demo** — https://project2.enaeble.co.kr

---

## 왜 대기열이 필요한가

동시 요청이 서버 처리량을 넘어서면 모두가 느려지고, 재고보다 많이 팔리는 문제가 생깁니다. 이 프로젝트는 두 가지를 나눠서 다룹니다.

- **줄 세우기** — 들어오는 요청을 순서대로 세우고 서버가 감당할 만큼만 통과시킨다
- **초과 판매 막기** — 통과한 요청들 사이에서도 재고 차감이 어긋나지 않게 한다

## 구현하면서 다룬 문제들

### 1. 선착순 순서를 어떻게 보장할 것인가

**접근.** Redis Sorted Set에 진입 시각을 score로 넣어 유저를 정렬했습니다. score가 작은 쪽이 먼저 들어온 사람이므로, 순서를 따로 관리하지 않아도 자료구조가 FIFO를 보장합니다. 내 순번은 나보다 앞에 있는 인원 수로 계산합니다.

### 2. 서버가 감당할 만큼만 들여보내기

**접근.** 백엔드 스케줄러가 1초마다 대기열 앞쪽에서 정해진 인원을 꺼내 활성 목록(Set)으로 옮깁니다. 활성 목록에 있는 유저만 결제 API를 호출할 수 있습니다.

전체 요청을 한꺼번에 받는 대신 통과 속도를 서버가 정하는 구조라, 뒤에서 밀려오는 트래픽이 결제 로직까지 도달하지 않습니다.

### 3. 재고보다 많이 팔리는 문제

**상황.** 재고 차감은 "지금 재고가 남았는지 확인" 다음에 "차감"입니다. 명령이 두 개라는 게 문제입니다. Redis는 명령 하나하나는 원자적으로 처리하지만, **두 명령 사이에 다른 요청이 끼어들 수 있습니다.** 재고가 1일 때 두 요청이 거의 동시에 들어오면 둘 다 "남아 있다"를 보고 둘 다 차감해서 재고가 -1이 됩니다.

**접근.** 활성 유저 확인, 재고 확인, 재고 차감을 Lua Script 하나로 묶었습니다. Redis는 스크립트를 통째로 하나의 명령처럼 실행하므로 그 안에서는 다른 요청이 끼어들지 못합니다.

> 락을 거는 방식과 비교하면, 락은 획득·해제 관리와 만료 처리가 따로 필요한 반면 이 경우는 연산이 짧아 스크립트 하나로 끝낼 수 있었습니다.

### 4. 내 순번을 어떻게 보여줄 것인가

**접근.** 클라이언트가 주기적으로 순번을 조회하는 폴링 방식으로 구현했습니다.

**트레이드오프.** 순번 갱신은 서버 → 클라이언트 단방향이라 SSE가 더 적합한 면이 있습니다. 다만 대기 인원이 많을수록 연결을 계속 유지하는 비용이 커지고, 순번은 초 단위로 갱신돼도 충분한 정보라 폴링으로 두었습니다. 실제 서비스라면 대기 인원 규모를 보고 다시 판단할 부분입니다.

## 동작 흐름

**1. 대기열 진입** — 유저가 진입 버튼을 누르면 Sorted Set에 현재 시각을 score로 추가됩니다. 이후 클라이언트는 자신의 순번을 주기적으로 조회합니다.

**2. 입장 허용** — 스케줄러가 매초 대기열 앞쪽 인원을 꺼내 활성 Set으로 옮깁니다. 활성 상태가 되면 화면이 결제 단계로 전환됩니다.

**3. 결제** — 결제 요청이 오면 Lua Script가 활성 목록 확인 → 재고 확인 → 재고 차감을 한 번에 처리하고, 조건을 만족하지 않으면 아무것도 바꾸지 않고 실패를 반환합니다.

## 알려진 한계

동시성 제어와 유량 제어를 직접 구현해보는 것이 목적이라, 아래는 다루지 않았거나 실제 서비스라면 다르게 갔을 부분입니다.

- **부하 테스트를 하지 않았습니다.** 로직상 초과 판매가 발생하지 않는 구조를 만드는 데까지가 범위였고, 실제 동시 요청을 발생시켜 검증하지는 않았습니다. k6나 Artillery로 검증하는 것이 다음 단계입니다.
- **대기 중 이탈을 처리하지 않습니다.** 창을 닫은 유저도 대기열에 남아 순번을 차지합니다. 활성 상태에 TTL을 걸거나 하트비트로 정리하는 방식이 필요합니다.
- **꺼낸 유저를 되돌릴 수 없습니다.** 대기열에서 꺼내는 순간 원본에서 제거되므로, 이후 처리에 실패해도 원래 순번으로 복구할 방법이 없습니다.
- **인증이 없습니다.** 클라이언트가 보낸 유저 식별자를 그대로 신뢰합니다. 활성 목록 확인으로 순서를 건너뛰는 것은 막지만, 신원 위조는 막지 못합니다.
- **결제는 시뮬레이션입니다.** 실제 PG 연동은 범위 밖입니다.
- **테스트 코드가 없습니다.**

## 프로젝트 구조

pnpm 워크스페이스 기반의 단일 저장소입니다.

```
.
├── services/   # 대기열 로직, Redis 연동, Lua Script 정의, API 핸들러
├── types/      # 프론트엔드와 백엔드가 공유하는 타입
├── views/      # 대기열 화면 UI
└── index.ts    # 서버 엔트리포인트 및 스케줄러 실행
```

## Getting Started

### 사전 요구사항

- Node.js 18 이상
- Redis 서버 (로컬 또는 원격)

### 실행

```bash
pnpm install
pnpm dev
```

Redis 접속 정보는 환경 변수로 지정하며, 지정하지 않으면 `localhost:6379`로 접속을 시도합니다.

## 배운 점

- **원자성은 자료구조가 아니라 연산 단위의 문제였다.** Redis가 싱글 스레드라 안전할 거라고 막연히 생각했는데, 안전한 건 명령 하나이지 내가 짠 로직 전체가 아니었습니다. "확인하고 바꾼다"가 두 명령으로 쪼개지는 순간 그 사이가 위험 구간이 된다는 걸 구현하면서 알게 됐습니다.
- **트래픽을 막는 것과 줄 세우는 것은 다르다.** 요청을 거절하면 사용자는 새로고침을 반복합니다. 순번을 보여주고 기다리게 하면 같은 지연이라도 경험이 달라지고, 서버는 통과 속도를 스스로 정할 수 있게 됩니다.
- **검증하지 않은 것과 동작하는 것은 다르다.** 로직상 초과 판매가 나지 않는 구조를 만든 것과, 실제로 나지 않는다는 걸 확인한 것은 별개라는 점을 정리하면서 분명해졌습니다.
